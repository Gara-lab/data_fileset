Purpose & context Gara is building a 3D graph editor application as a static web page hosted on a Git repository. The project uses native ES modules (no bundler) with Three.js (including OrbitControls and TransformControls) as the primary rendering dependency. Gara manages a two-AI workflow: Claude acts as architecture lead, producing modular contract documents that a separate coding AI (Qwen) then implements in JavaScript. The architecture follows a strict layered dependency order: core/ → domain/ → services/ → workflows/ → ui/ → main/, with dependency direction enforced throughout. --- Current state Contracts are complete for: Domain layer: Node.js, Link.js, Graph.js, GraphValidation.js, and five domain operations Services: RendererService.js, CameraService.js, InteractionService.js, SelectionService.js, PersistenceService.js Workflows: CreateNodeWorkflow.js, DeleteNodeWorkflow.js, MoveNodeWorkflow.js, ConnectNodesWorkflow.js, DisconnectNodesWorkflow.js, SelectNodeWorkflow.js, ExportGraphWorkflow.js, ImportGraphWorkflow.js UI layer: UIPanels.js, UIBindings.js Test structure: Defined for domain layer only; broader coverage deferred until full build is running One open issue is blocking main/: transient "connect mode" interaction state in UIBindings.js does not belong to SelectionService or the Domain — a decision on where this state lives is needed before main/ contracts can be written. --- Key learnings & principles Critical rules established through experience and correction: Exact file names required: Every contract must specify the exact PascalCase implementation file name. No index. files anywhere except main/. One contract = one file; no merging permitted. (Violation caused Qwen to collapse modules into single index.ts files, requiring full rewrite.) Decisions before writing: Ask all open design decisions first, wait for Gara's approval, then write only that contract — nothing else appended (no bundled recommendations or next-step prompts). Rollback rule: Workflows pairing a Domain mutation with a Service sync call must roll back via the inverse Domain operation if sync fails, returning a distinct SyncFailedRolledBack failure. Applies to Create/Connect-style workflows; does not* apply to Delete/Disconnect-style workflows (rollback would fabricate new IDs). Incremental edits only: When amending an already-implemented file, the coding AI outputs only the specific addition and its insertion location — never a full file rewrite. Clean contract on approval: If a contract is approved but not yet sent to Qwen, rewrite it cleanly incorporating any amendments — do not issue a base contract plus a separate patch. Two contracts per response maximum: Acceptable only when each is confidently under 250 lines; never more than two at once. --- Approach & patterns Contract-first, implementation-second workflow: Claude writes architecture contracts; Qwen implements them Strict sequential process: decisions → approval → single clean contract output Modular, one-file-per-contract discipline enforced throughout Test coverage intentionally scoped narrow (domain only) until the full build is validated

1. File Discipline
Every approved contract must result in a physically saved file, at the exact folder path and exact filename given in the contract — casing included (e.g. UIBindings.js, never UIBinding.js). Before saying a task is done, confirm the file exists on disk at that exact path, not just that code was generated in the chat response.
One contract = one file. Never merge multiple contracts' logic into a shared or index.* file, even within the same folder.
If an import path changes due to an earlier correction (e.g. core/events.js → core/events/EventBus.js), every file referencing the old path must be updated, not just the one file being actively worked on — a global find of the old path is required before considering a fix complete.
2. Editing Existing Files
When asked to add or change something in an existing file: output only the new/changed code plus its exact insertion point. Never regenerate or rewrite the entire file.
Before applying an edit, show the current, exact content of the section being modified — don't assume or reconstruct it from memory. This prevents duplicated blocks (like the orphaned duplicate catch block that appeared in UIPanels.js).
After every edit, verify brace/bracket balance in the modified region specifically — syntax errors caused by incomplete edits are not acceptable deliverables.
3. When Told "No Code to Change"
Only say this after actually locating and showing the relevant existing code that already satisfies the request. Never say it as a way to skip an unclear or additive instruction — if the instruction asks for something new and nothing exists yet, write it.
4. Version Accuracy
When using a pinned library version (e.g. Three.js 0.170.0, declared in the import map), use APIs correct for that exact version — check for breaking changes between versions rather than defaulting to older/newer API shapes from general familiarity (e.g. TransformControls.getHelper() requirement in modern Three.js).
5. Test Command Sanity
Any test script added to package.json should be verified to actually run successfully in a plain terminal before being considered complete — not just written and assumed correct.
